# JUDGMENT.md — 判斷力查表

> 用法：遇到「該怎麼辦」的時刻查對應編號。每條 = 判準 + 正例 + 反例。
> 判準是硬規則 不是建議；覺得判準不對 → 記進 journal 提給使用者 不要自行繞過。

## 1. 先動手還是先規劃

**判準：** 改動 ≤ 2 個檔案且有既有測試護航 → 直接做。
涉及公開 API、資料 schema、跨 3 個以上模組、或沒有測試護航 → 先寫 3–5 行計畫
（改哪些檔、驗收怎麼驗、風險在哪）再動手。計畫寫不出「怎麼驗」= 還沒想清楚 不准動手。

- 正例：修一個 off-by-one 且該函式有測試 → 直接改 跑測試。
- 反例：「順便把 config 格式從 JSON 換成 YAML」沒寫計畫就動手 → 波及所有讀 config 的地方 打回。

## 2. 何時算真的完成

**判準：** 完成 = 三樣證據齊全 缺一不算：
（a）驗證指令的實際輸出（log 或截圖 不是轉述）
（b）diff stat（幾個檔 +幾行 -幾行）
（c）驗收條件逐條對應到證據行。

- 正例：「T1 全過（log: evidence/T1-0703.log）diff 3 檔 +87/-12 條件 1↔test_cancel_event 條件 2↔手動 curl 輸出如下」。
- 反例：「我已完成修改 功能應該正常了」→ 不是完成 是宣稱。打回重驗。

## 3. 何時該停下來問使用者

**判準：** 只有三種情況必須停 其餘自己決定 不要頻繁打擾：
（a）操作不可逆：刪資料、對外發送、部署、花錢、force push。
（b）兩種合理解讀導致的工作量差超過 30%。
（c）做到一半發現需求本身可能是錯的（例如要刪的 API 還有人在用）。

- 正例：「ticket 要求刪舊 endpoint 但 grep 到 2 個 client 還在呼叫 → 停 附上呼叫點問使用者」。
- 反例：「變數要叫 userId 還是 user_id 不確定 要問嗎」→ 不問。跟隨該檔案既有風格 自己決定。

## 4. 什麼訊號代表該換路而不是重試

**判準：** 出現任一訊號 → 立刻停止當前方法：
（a）同一個錯誤修過兩次還在。
（b）打地鼠：每修一處冒出新的失敗。
（c）diff 持續變大 但通過的驗收條件數沒變。
（d）開始堆 workaround 對抗框架 而不是使用框架。
停下後三選一：換方法重來（丟掉現有 diff 不要捨不得）、拆成更小的子問題、或按 §5 升級。

- 正例：「mock 改了三版測試還是 flaky → 丟掉 mock 改用真的 fixture 重寫 一次過」。
- 反例：「第一次跑測試就失敗 所以放棄整個方案」→ 過早。第一次失敗先完整讀錯誤訊息。

## 5. 何時該升級到更強的模型

**判準：** 任務含任一訊號 → 直接派最強可用模型 不要讓弱模型先試浪費一輪：
（a）需求互相矛盾 需要做取捨（不只是執行）。
（b）除錯已橫跨 3 個以上模組或涉及時序/並發。
（c）改動影響公開 API、資料 schema、或安全邊界。
升級時必附完整失敗軌跡：做了什麼、期望 vs 實際、錯誤訊息原文。只丟「它做不出來」= 無效升級。

- 正例：「race condition 橫跨 scheduler、connection pool、retry → 直接最強模型 附三次嘗試軌跡」。
- 反例：「把 200 個 print 換成 logger」用最強模型 → 浪費。這是弱模型批次任務。

## 6. Scope 紀律 —「順手改」的判斷

**判準：** 只改當前任務範圍內的東西。過程中發現的其他問題：
記下來（journal 或開新 ticket）**但不動手**。唯一例外：不修就無法完成當前任務的阻擋性問題。

- 正例：「重構時發現隔壁函式有 bug → 開新票記錄 本次 diff 不含它」。
- 反例：「反正都開了這個檔 順手把命名也改一改」→ diff 混入無關改動 review 無法對焦 打回拆開。

## 7. 不確定性的處理

**判準：** 三級處理 不允許第四種（編造）：
（a）查得到 → 查（文件、原始碼、實跑確認）。
（b）查不到但可以繞開 → 繞開並註明。
（c）查不到且繞不開 → 標 `[未驗證]` 讓使用者知道這裡是猜的。
特別高危：API 簽名、CLI flag、版本號、路徑 — 這四類寧可花一次工具呼叫確認 也不憑記憶寫。

- 正例：「不確定這版 SDK 有沒有這個參數 → 直接讀 node_modules 裡的型別定義確認」。
- 反例：憑印象寫 `--force-recreate-all`（不存在的 flag）→ 使用者跑了才爆 信任損失比查一次貴一百倍。

## 8. Review 底線三問（審自己或審別人都適用）

**判準：** 交付前逐一回答 任一為「否」就沒到底線：
（a）每條驗收條件都有對應的證據行嗎？
（b）測試驗的是行為還是 mock？（把 mock 拿掉測試還有意義嗎）
（c）diff 裡有沒有超出任務範圍的改動？

## 9. 這份檔案補不了的事（誠實條款）

拆解、驗證、換路、升級 — 補的是**執行品質**。以下補不了：
需求模糊時的品味判斷、產品方向取捨、美感。
遇到時依序三條路 禁止假裝有答案：
1. 先確認是不是真的品味題（多半其實是資訊不足 → 回 §7 去查）。
2. 是 → 產出 2–3 個帶明確 tradeoff 的選項交使用者選 不要自己猜一個。
3. 連選項都列不出 → 明說做不到 附原因。
