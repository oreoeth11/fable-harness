# DISPATCH.md — 派工與驗證守則

## 1. 指揮官不下場（門檻是可數的 不是感覺）

主對話的 context 是最稀缺資源。以下情況一律派 subagent 主對話只收結論：
- 要讀 **超過 3 個檔案** 或 **超過 200 行** 才能回答 → 派唯讀偵察（scout）。
- 要 **網路搜尋超過 2 次** → 派研究 agent。
- 要 **改超過 2 個檔案** 或屬機械式批次（改名、換 API、格式化）→ 派實作 agent。
- 主對話自己只做：讀 harness 檔、做決策、≤ 20 行的關鍵修改、整合結論。

## 2. 派工三件套（缺一不派）

1. **目標與動機** — 做什麼 + 為什麼。動機讓 agent 在邊界情況知道怎麼取捨。
2. **驗收條件** — 可斷言優先：「test_x 通過」優於「功能正常」。
3. **回報格式** — 結論結構 + 長產物落檔路徑。

模板在 docs/templates/delegate.md 直接填空。

## 3. 模型分派（落地前先查環境實際可用型號 替換掉層級代稱）

| 層級 | 用於 | 不用於 |
|------|------|--------|
| 小（快便宜） | 掃 repo、grep、批次套用已解出的模式、摘要 | 跨檔推理的實作 |
| 中（預設） | 實作、重構、寫測試、review、一般除錯 | 架構決策、模糊需求 |
| 大（省著用） | 架構取捨、跨模組/並發除錯、升級終點、多方案評審 | 機械任務（浪費） |

## 4. 回報合約

- Subagent 只回 **結論 + 檔案:行號**。超過 50 行的產出落檔 回傳路徑。
- 唯讀偵察的結論不必複驗；**任何修改宣稱必須走 §6 驗證** 無例外。

## 5. 升降級路徑

- 小模型同一子任務 **錯 1 次** → 升中 不重試。
- 中模型同一子任務 **連錯 2 次** → 帶完整失敗軌跡升大（軌跡定義見 JUDGMENT §5）。
- 大模型解出模式 → 寫成步驟化指令 **降回小模型批次套用**。
- 同一方法 **最多兩輪** 之後必須換路（JUDGMENT §4）。

## 6. 驗證不自驗（作者對自己的 bug 是盲的）

| 產出類型 | 驗法 |
|----------|------|
| 檔案落地 | fresh agent read-back：存在、非空、關鍵段落在 |
| 程式碼 | 測試或實跑 附輸出。不接受「我檢查過了」 |
| 高風險判斷（架構/資安/不可逆） | 第二意見：fresh context 同輸入比對結論；或出 3 案由審查者選優 |

審查者必須是 **fresh context** — 不得由實作的同一個 agent 續跑審查。
審查輸出只有兩種：`PASS` 或 `FAIL + 問題清單（檔案:行號 + 期望 vs 實際）`。
「大致沒問題」不是合法輸出。
